# FoundationKit Typed Client Generation v1

## Problem

FoundationKit already derives deterministic Postman from runtime OpenAPI, but the Blazor/frontend boundary still required hand-written HTTP calls and duplicated request/response models. That breaks the intended contract flow:

```text
Backend contracts / endpoint metadata
        ↓
runtime OpenAPI
        ↓
Postman + typed client
        ↓
frontend UI
```

Phase 13 adds the first typed-client foundation before the visual design-system/template phase.

## Evidence

The same live OpenAPI document produced by a Composer-generated executable product is used to generate C# source deterministically. CI then compiles that source against `FoundationKit.Blazor` and executes the generated client against the same running API.

The runtime proof covers:

```text
Create
→ Location metadata
→ Get
→ ETag + CorrelationId metadata
→ Update with If-Match
→ refreshed ETag
→ List with query parameters
→ Delete
→ 404 after delete
```

This proves the client is not merely syntactically generated; it can consume the FoundationKit CRUD/API contract that produced it.

## Scope

`generate-csharp-client-from-openapi.py` is intentionally **not** a general-purpose OpenAPI generator. Its v1 input contract is the current FoundationKit CRUD/API Engine surface.

It selects only operations that publish both:

```text
x-foundation-module
x-foundation-operation
```

Supported Foundation operations:

```text
list
get
create
update
delete
```

Supported transport features are deliberately bounded:

- OpenAPI 3.x;
- local `#/components/schemas/...` references;
- named object component schemas;
- arrays;
- strings;
- UUID strings → `Guid`;
- date-time strings → `DateTimeOffset`;
- int32/int64;
- float/double;
- Boolean values;
- path/query/header parameters;
- repeated query-array values;
- JSON request bodies;
- JSON success responses;
- no-content success responses;
- Foundation `Idempotency-Key` and `If-Match` headers.

Unsupported schema/ref/parameter shapes fail closed rather than producing partial C#.

## Blazor transport metadata

The existing `ApiResult` and protected `ApiClientBase.SendAsync` contracts remain intact.

Phase 13 adds:

```csharp
ApiResponseMetadata
ApiResponse
ApiResponse<T>
```

with transport metadata currently containing:

```text
ETag
Location
CorrelationId
```

`ApiClientBase` adds additive protected methods:

```csharp
SendWithMetadataAsync(...)
SendWithMetadataAsync<T>(...)
```

The legacy result-only methods delegate to the metadata-aware path and return the same `ApiResult` shape as before. This avoids changing `ApiResult` equality/constructor semantics while giving generated clients the metadata needed for optimistic concurrency and navigation after create.

## Generated C# shape

The deterministic output contains:

```text
// <auto-generated />
DTO records with JsonPropertyName attributes
one typed client derived from ApiClientBase
Foundation CRUD methods
bounded query-string construction
explicit idempotency/concurrency header parameters
ApiResponse<T> / ApiResponse return values
```

Authentication is intentionally not synthesized into request DTOs. The consumer configures the `HttpClient`/handler according to its real identity integration. The Phase 13 runtime proof uses the bounded Phase 12 reference authentication headers only as executable evidence.

## Determinism

For the same runtime OpenAPI document, namespace, class name, and generator version, the generated C# bytes are deterministic.

The CI proof:

```text
capture live OpenAPI
→ generate C# client
→ SHA-256
→ generate again
→ same SHA-256
→ --check
→ compile
→ execute against live API
```

No timestamp, machine path, random identifier, token, password, or environment secret is written into generated client source.

## Compatibility

- `FoundationKit.Blazor.ApiResult` is unchanged;
- existing subclasses using `SendAsync` require no source migration;
- metadata-aware APIs are additive;
- package count remains 17;
- Composer schema v1/v2 generation is unaffected;
- runtime OpenAPI remains canonical; no second DTO/request model is introduced in Composer or UI tooling.

## Contract versioning

Phase 13 is additive and does not redefine the existing Blazor capability contract or API Engine transport semantics. The current capability contract version therefore remains unchanged.

A breaking change to the typed-client generation contract must either:

- introduce an explicitly versioned generator contract/output mode; or
- follow FoundationKit's normal breaking/deprecation policy for public runtime APIs.

Generator support for a new OpenAPI shape is added only with deterministic generation plus compile/runtime evidence.

## Tests

Repository tests cover the new `FoundationKit.Blazor` response metadata path:

- successful ETag/Location/CorrelationId capture;
- metadata on typed failure responses;
- legacy `SendAsync<T>` behavior remains result-only;
- network failure returns the same failure result with empty metadata.

The dedicated typed-client workflow supplies integration evidence from live runtime OpenAPI and executes all generated CRUD transport paths used by the first frontend phase.

## Migration

Existing manually written API clients can continue unchanged.

New frontend work should prefer this flow:

```text
runtime OpenAPI
→ generated typed C# client
→ ViewModel / UI
```

A consumer may wrap or extend the generated client at its own business/application boundary, but should not hand-copy the generated transport DTOs and request paths into a parallel client contract.

## CI

`FoundationKit Typed Client Proof` is the dedicated Phase 13 gate. It:

1. generates the Phase 12 executable reference product;
2. starts SQL Server and the generated API;
3. captures live OpenAPI;
4. generates/reproduces/checks the C# client;
5. creates a tiny proof project referencing the exact-head `FoundationKit.Blazor` project;
6. builds and runs the typed client against the live API;
7. uploads the live OpenAPI, generated client, runtime proof, and API log.

Normal Core CI, Composer generation, full-stack A/B proof, package integrity, Security Scan, CodeQL, and Windows Manager checks remain required before merge.

## Acceptance criteria

Phase 13 is complete only when one exact PR head proves:

```text
existing ApiClientBase behavior compatible
+ metadata-aware Blazor transport tests green
+ bounded generator fails closed
+ live runtime OpenAPI is the generator input
+ generated C# is deterministic
+ --check detects drift
+ generated client compiles against exact-head FoundationKit.Blazor
+ generated client executes Create/Get/Update/List/Delete
+ Location/ETag/CorrelationId reach the caller
+ no duplicate hand-authored transport contract is introduced
+ 17-package boundary unchanged
+ normal CI/security/review gates green
```

Passing this phase provides the typed transport/client foundation for the next frontend increments: reusable UI primitives/design system, then first-party Admin/User templates and visual Studio composition.
