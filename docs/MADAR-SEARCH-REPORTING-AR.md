# البحث والتقارير التشغيلية في مدار

يوثق هذا الدليل شريحة **Madar v0.10** الخاصة بالبحث المصرح والتقرير التشغيلي المحدود. هذه القدرة مملوكة لمنتج مدار، ولا تمثل حزمة بحث أو تقارير عامة في FoundationKit.

## الهدف

يوفر مدار استعلامًا موحدًا يعيد صفحة حالات وملخصًا تشغيليًا من **نفس مجموعة البيانات المصرح للمستخدم برؤيتها**. لذلك لا يمكن لعدد النتائج أو عدادات التقرير أن تكشف حالة لا يستطيع المستخدم قراءتها أصلًا.

نطاق القراءة الحالي لم يتغير:

- منشئ الحالة يستطيع رؤيتها.
- الموظف المسندة إليه الحالة يستطيع رؤيتها.
- الدور الذي يملك `madar.cases.read-all` يستطيع القراءة عبر جميع الحالات.

يتم تطبيق هذا النطاق قبل أي فلتر وقبل حساب أي عداد في التقرير.

## واجهة API

المسار:

`GET /api/cases/search`

يتطلب جلسة مصادقة صالحة. الفلاتر المدعومة:

- `query`: نص في العنوان أو الوصف، أو معرف حالة كامل؛ الحد الأقصى 200 حرف.
- `caseType`: نوع الحالة المعتمد في مدار.
- `priority`: `low` أو `medium` أو `high` أو `critical`.
- `status`: `new` أو `assigned` أو `in-progress` أو `resolved` أو `closed`.
- `slaState`: `not-applicable` أو `active` أو `met` أو `breached`.
- `departmentId`: معرف القسم.
- `assignedToUserId`: معرف الموظف المسند إليه.
- `createdFromUtc` و`createdToUtc`: نطاق تاريخ إنشاء متسق لا يتجاوز 366 يومًا عند تحديد الطرفين.
- `offset`: من 0 إلى 10000.
- `limit`: من 1 إلى 100، والافتراضي 25.

الترتيب حتمي: `UpdatedUtc` تنازليًا ثم معرف الحالة، وتطبق الصفحة بعد جميع قيود الصلاحيات والفلاتر.

## الملخص التشغيلي

الاستجابة تعيد `items` و`total` و`offset` و`limit` بالإضافة إلى `summary` الذي يحتوي:

- الإجمالي.
- غير المسندة.
- أعداد `new` و`assigned` و`in-progress` و`resolved` و`closed`.
- أعداد SLA: غير مطبق، نشط، محقق، مخترق.

كل هذه العدادات محسوبة من الاستعلام المصرح والمفلتر نفسه، قبل `Skip/Take`، وليست من جميع الحالات في قاعدة البيانات.

## الواجهة العربية

المسار:

`/reports/cases`

توفر الصفحة فلاتر البحث الأساسية، بطاقات ملخص تشغيلي، جدول النتائج، والتنقل بين الصفحات. فتح الحالة يعيد استخدام صفحة تفاصيل الحالة الحالية، لذلك تبقى سياسة الوصول المركزية هي المرجع النهائي.

## الخصوصية والأمان

- لا يوجد مسار بحث مجهول؛ مجموعة `/api/cases` تتطلب المصادقة.
- المستخدم العادي لا يحصل على `read-all` ضمنيًا بسبب استخدام صفحة التقارير.
- الحالات المخفية لا تدخل في الصفوف ولا `total` ولا عدادات `summary`.
- البحث SQL-backed ومعلّم بالـparameters من EF Core؛ لا يتم تركيب SQL يدويًا من نص المستخدم.
- هذه القراءة لا تنشئ حدث Audit لكل استعلام في v0.10 لتجنب سجل تدقيق عالي الضوضاء. أحداث دورة حياة الحالة تبقى كما هي.
- لا يتم البحث داخل محتوى المرفقات.

## حدود المرحلة

لا تشمل v0.10:

- Elasticsearch أو OpenSearch أو Lucene أو مزود فهرسة خارجي.
- Full-text search أو OCR أو فهرسة محتوى المرفقات.
- Saved searches أو تقارير مجدولة.
- CSV/PDF exports أو مشاركة التقارير.
- رسوم بيانية أو BI integration.
- تقارير متعددة المستأجرين أو شجرة مؤسسية.
- إنشاء `FoundationKit.Search` أو `FoundationKit.Reporting`.
- أي ادعاء Production Approval أو SoD أو اعتماد أمني خارجي.

## دليل التحقق

يغطي الاختبار الآلي قواعد المصادقة والتطبيع والحدود ونطاق `read-all`. ويضيف SQL/E2E مجموعة حالات تحمل marker واحدًا بحيث:

1. ينشئ Administrator حالة تبقى مخفية عن Operator.
2. ينشئ Operator حالة يملكها.
3. ينشئ Administrator حالة ثم يسندها إلى Operator.
4. بحث Operator يعيد الحالتين المرئيتين فقط، وتبقى الحالة المخفية خارج الصفوف والعدادات.
5. بحث Administrator يعيد الحالات الثلاث بفضل `madar.cases.read-all`.
6. يتم التحقق من فلاتر الحالة والأولوية وصفحتين بحجم 1 ومن رفض قيم البحث غير الصالحة.

يبقى ناتج الحزم العامة مستقلًا عن هذه القدرة: لا تُضاف أي حزمة FoundationKit جديدة بسبب حاجة منتج واحد.
