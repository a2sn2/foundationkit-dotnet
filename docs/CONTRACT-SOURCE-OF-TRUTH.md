# FoundationKit Contract Source of Truth

## Purpose

FoundationKit does not allow transport contracts to evolve independently in backend code, Swagger, Postman, and later frontend clients. A request model must have one authoritative definition path and every derived representation must be reproducible from it.

The Phase 8 contract chain is:

```text
C# Request / Response contracts
+ Module API configuration
+ Endpoint / ApiExplorer metadata
                 |
                 v
        Runtime OpenAPI document
       canonical transport contract
                 |
        +--------+---------+
        |                  |
        v                  v
    Swagger UI      Deterministic Postman
                           |
                           v
                 future typed client input
```

The C# contract and module configuration remain the implementation source. Runtime OpenAPI is the canonical serialized transport contract because it is produced by the actual running endpoint surface. Postman is a derived artifact and never a second authoring surface.

## Why runtime OpenAPI

Static DTO inspection alone is not enough to describe an HTTP contract. The effective contract also contains:

- route templates and HTTP methods;
- path, query, and header parameters;
- required versus optional headers;
- request and response media types;
- Problem Details responses;
- authorization/security metadata exposed by the host;
- pagination/filter/sort parameters;
- idempotency and concurrency preconditions;
- concrete schemas produced by the configured ASP.NET Core/OpenAPI pipeline.

Capturing OpenAPI from a running Workbench therefore proves the same endpoint metadata that clients actually see.

## Ownership rules

### Backend contracts

Request/response types, DataAnnotations, module configuration, endpoint mappings, and API metadata are edited in C#.

### OpenAPI

OpenAPI is generated from the runtime application. The repository does not maintain a second hand-written Swagger contract.

### Postman

`postman/FoundationKit.Workbench.postman_collection.json` is generated by:

```bash
python3 scripts/generate-postman-from-openapi.py \
  workbench-swagger.json \
  postman/FoundationKit.Workbench.postman_collection.json
```

Do **not** edit generated Postman requests manually. If a backend contract changes, run the application, capture its OpenAPI document, and regenerate the collection.

The generator also supports a strict drift check:

```bash
python3 scripts/generate-postman-from-openapi.py \
  workbench-swagger.json \
  postman/FoundationKit.Workbench.postman_collection.json \
  --check
```

## Determinism contract

The generator must produce byte-identical output for byte-equivalent OpenAPI input and the same explicit options.

It therefore does not use:

- current timestamps;
- random UUIDs;
- network lookups;
- machine-specific paths;
- environment-specific ordering;
- nondeterministic dictionary/set iteration for serialized output.

The collection identifier is a stable UUID5 derived from the OpenAPI title/version. Operations, folders, parameters, and generated examples use deterministic ordering and values.

CI generates the same collection twice and uses byte comparison to prove reproducibility.

## Drift gate

The Workbench SQL integration job performs this sequence on every affected PR:

```text
Start real Workbench + SQL Server
        |
        v
Capture /swagger/v1/swagger.json
        |
        v
Verify structural OpenAPI expectations
        |
        v
Generate Postman A from OpenAPI
        |
        v
Generate Postman B from same OpenAPI
        |
        v
A == B byte-for-byte
        |
        v
A == committed Postman byte-for-byte
        |
        v
--check committed Postman
        |
        v
Run real HTTP/SQL behavior smoke
```

This means a DTO, route, parameter, or header change cannot silently leave the committed Postman collection stale.

## Contract versus behavior

A generated Postman collection represents the transport contract. It does not replace executable behavior tests.

For example, OpenAPI can state that `If-Match` is required and `412` is possible. Only the SQL/runtime smoke proves that a stale ETag actually returns `412`, that a valid ETag updates the correct database row, and that the new ETag advances.

FoundationKit therefore separates:

- **contract evidence** — runtime OpenAPI + deterministic Postman;
- **behavior evidence** — unit/integration/security tests and Workbench SQL smoke.

Neither one substitutes for the other.

## Generated examples

The Postman generator creates safe deterministic examples from OpenAPI schemas. Examples are intended to make the collection structurally usable, not to invent product business semantics.

Current deterministic examples include bounded placeholders for:

- strings;
- numbers and booleans;
- UUIDs;
- dates/date-times;
- email/URL formats;
- arrays and nested objects;
- enum first values;
- required API headers such as `Idempotency-Key` and `If-Match`.

Read-only schema properties are not inserted into request bodies.

## Generator v1 boundaries

The current generator deliberately supports the contract surface proved by Workbench:

- OpenAPI 3.x JSON;
- local `#/...` references;
- ordinary object/array/primitive schemas;
- `allOf` composition;
- JSON request bodies;
- path/query/header parameters;
- tagged operations.

It does not yet claim full support for every OpenAPI feature, including external references, arbitrary multipart/file examples, advanced callbacks, or every `oneOf`/`anyOf` discrimination pattern. Those should be added only when a real FoundationKit capability requires and tests them.

Unsupported contract features must fail visibly rather than silently producing a misleading client artifact.

## Security

Generation happens from the locally captured runtime OpenAPI document. CI does not fetch arbitrary external schemas or URLs.

The generator is Python-standard-library only and does not execute values from the OpenAPI document. Generated examples are deterministic placeholders rather than copied secrets or runtime data.

Actual authentication credentials/tokens must never be embedded into the committed generated collection. When security schemes are later present in the canonical OpenAPI contract, their client representation must use variables/placeholders and follow the same no-secret rule.

## Typed clients

Phase 8 intentionally stops at the stable derivation boundary:

```text
Runtime OpenAPI -> deterministic derived artifact
```

A future typed frontend client should consume this same canonical OpenAPI contract rather than creating a third hand-maintained request model. Phase 8 therefore establishes the prerequisite for typed-client generation without coupling the current backend phase to a frontend framework.

## Compatibility

Phase 8 changes no reusable runtime package API. It changes repository tooling and ownership of the Workbench Postman artifact.

The reusable package count remains 17. Existing applications are unaffected unless they choose to adopt the same derivation workflow.

## Acceptance criteria

Phase 8 is complete only when the exact head proves:

- repository/build/test/package/security gates remain green;
- Workbench boots against SQL Server;
- runtime OpenAPI structural verification passes;
- deterministic Postman generation succeeds twice;
- both generated files are byte-identical;
- generated Postman equals the committed collection byte-for-byte;
- `--check` reports synchronized;
- generated Postman is valid JSON and uploaded as CI evidence;
- Phase 7 runtime behavior smoke remains green;
- no new runtime package is introduced.
